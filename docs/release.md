# Development and releases

## Modules

The repository contains five published Go modules and one test module:

| Directory | Purpose | First release tag |
| --- | --- | --- |
| Root | Core | v0.1.0 |
| driver/pgx | PostgreSQL | driver/pgx/v0.1.0 |
| driver/sqlite | SQLite without an engine | driver/sqlite/v0.1.0 |
| cli/urfavecli | urfave/cli v3 | cli/urfavecli/v0.1.0 |
| cmd/xmigrator | Installable binary | cmd/xmigrator/v0.1.0 |
| internal/integration | Integration tests | Not published |

Published manifests use real dependency versions without local replace directives. The test module uses relative replacements to test the checkout with GOWORK=off. The local go.work is ignored by Git and generated by the workspace command.

## Local checks

```sh
go run tools/dev.go workspace
make test
make build
./build/xmigrator --help
```

Running go test ./... from the root does not traverse nested modules. tools/dev.go explicitly visits all six. make test runs short checks; a full check requires a dedicated PostgreSQL database that tests may clear:

```sh
export XMIGRATOR_TEST_PG_DSN='postgres://postgres:postgres@localhost:5432/xmigrator_test?sslmode=disable'
make check
make verify-install
```

make check runs vet, race, real PostgreSQL/SQLite integration tests, and executable tests. It merges coverage and requires 100% statement coverage for production packages. Artifacts are in .artifacts/. make sqlite-check runs the available SQLite matrix without PostgreSQL and does not replace a full check.

make verify-install builds a temporary Go proxy from the checkout, uses a clean module cache and GOWORK=off, and installs the binary using release manifests without replacements. It does not publish modules. make prove-regressions temporarily introduces and restores bugs to verify regression tests; do not edit source concurrently.

CI checks PostgreSQL 14/17/18 on Linux and SQLite on macOS/Windows. A successful local run does not replace results from that matrix. Keep code, README, skills, and documentation in English.

## Preparing a version

The first release's dependency versions and installation verification use v0.1.0. When changing the version, update requirements for repository modules in all published manifests together with version/replacements in tools/dev.go. Local replacements must not appear in published go.mod files.

Before tagging:

1. Review the changes, documentation, and release [changelog](../CHANGELOG.md), then create the release commit.
2. Obtain successful full check, verify-install, and CI results for that commit.
3. Verify LICENSE in every published module and ensure build, .artifacts, go.work, credentials, and database files are excluded from release files.
4. Match dependent module versions to the tags that will be published.

## Publishing

Go modules in subdirectories require tags prefixed with their directory. For the first coordinated release, all five tags must point to the verified release commit. Publish the core first, then drivers/adapter, then cmd. internal/integration gets no tag and is not installed by users.

After publishing, verify downloads through the normal Go proxy in a clean environment with GOWORK=off:

```sh
go install github.com/sxwebdev/xmigrator/cmd/xmigrator@v0.1.0
xmigrator --version
xmigrator --help
```

In a separate temporary application, run go get for the core and chosen driver at v0.1.0 and build a minimal example. Before publication, verify-install checks packaging but does not confirm tag availability through the public proxy. Do not move published tags; release fixes under a new version.
